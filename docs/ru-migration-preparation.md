# Подготовка российского размещения РЯДОМ

Дата: 29.10.2026. Это подготовка, не выполненный перенос. Никаких новых
production-подключений, автоматической установки, экспорта данных, смены DNS или
секретов этот PR не добавляет. Существующие рабочие функции сохраняются.

## Решения и открытые условия

- Владелец поручил подготовить перенос в РФ; отключение аккаунтов как продуктовый
  вариант отклонено. Покупка сервера и переключение ещё не согласованы.
- Основной бюджетный кандидат — AdminVPS Start, заявлено 1 289 ₽/мес.,
  4 vCPU / 8 GB / 80 GB NVMe. Цена и наличие в кабинете не проверены;
  это не подтверждённая смета и не заключение о соответствии закону.
- Перед оплатой получить сведения о российской площадке и копиях, условиях
  обработки ПД, договоре/поручении, IPv4, SMTP 465, Docker и лимите трафика.
  Бесплатное администрирование нельзя считать сопровождением Supabase без
  письменного уточнения. Еженедельная копия не заменяет ежедневную копию БД.
- Нельзя переносить реальные данные на неподтверждённую площадку.
- Покупка российского VPS сама по себе не закрывает требования 152-ФЗ:
  нужны оценка угроз/уровня защищённости и меры в пределах ответственности сторон,
  согласия, сроки, уведомления РКН и карта внешних получателей.

## Проверка кандидата без изменения сервера

На выбранном Linux-сервере ответственный инженер запускает:

```sh
python3 scripts/ru-migration-preflight.py --path /opt
```

Путь должен существовать и находиться на диске, где будут данные. Если для медиа
выделен иной диск, проверить и его отдельно. Скрипт ничего не устанавливает,
не читает окружение/ключи, не обращается к БД и не меняет конфигурацию.
Проверяет память, CPU, свободный диск, Docker daemon и Compose. Docker-команды
используют текущий Docker context; соответствие daemon этому хосту инженер
проверяет отдельно. Отсутствие прав на daemon считается непрохождением проверки,
не исправляется автоматическим sudo или изменением прав socket.

Рекомендуемый ориентир — 4 CPU, номинальные 8 GB RAM и диск 80 GB+; тест учитывает,
что Linux показывает меньше рекламного объёма. Порог малого стенда — 2 CPU,
3.5 GiB видимой RAM и 35 GiB свободного места. Прохождение этого экрана НЕ
подтверждает достаточность под нагрузкой, безопасность, российское размещение
или готовность переноса. Все эти отметки в JSON остаются false.

## Порядок репетиции

1. Подтвердить поставщика, площадку, договорные условия, бюджет, доступ и копии.
   Создать закрытый стенд, HTTPS, отдельные секреты, firewall и ограниченный
   административный доступ. Не публиковать Studio и прямой Postgres без защиты.
2. Зафиксировать совместимые версии PostgreSQL 17, Auth, Storage и Edge Runtime.
   В штатном self-hosted наборе версия Postgres может отличаться от production.
   Не копировать compose из непроверенного стороннего шаблона.
3. Существующие custom-архивы октября сохраняются; не объявлять их повреждёнными
   из-за несовместимости с новой установкой. Их чтение уже проверено, полное
   восстановление — нет. Для нового контура сначала проверить совместимость
   схем, ролей и расширений на изолированном стенде. Свежий экспорт потребует
   отдельного согласованного копирования данных и закрытого хранения.
4. Использовать актуальное руководство Supabase для platform → self-hosted:
   оно разделяет роли/схему/данные; не восстанавливать весь raw-dump поверх
   служебных схем вслепую. Не исключать непонятные таблицы/колонки только ради
   зелёного результата. Учесть пользователей Auth, идентичности и связи.
5. Storage: отдельное копирование содержимого, прав бакетов и метаданных.
   Проверить приватность и signed URLs. Сравнить числа, размеры и хеши файлов;
   список `storage.objects` не является копией самих медиа.
6. Friends SQLite: согласованный SQLite online backup, проверка целостности,
   отдельный config. Обычный cp активного файла без учёта WAL не использовать.
7. Настроить все семь серверных функций и внешние интеграции. При новых ключах
   пользователям потребуется повторный вход; не обещать сохранение сессий.
   Проверить email/password, восстановление пароля, VK/Яндекс на телефоне,
   callbacks/state, владельца `city='*'` и городские ограничения.
8. Проверить сценарии жителя/модератора/владельца: объявления и стена через
   модерацию; комментарии/ответы; приватные сообщения; истории и личный архив;
   медиа; друзья/добровольная геопозиция; заявки организаций; push по выбору.
9. Проверить отдельные согласия и серверные квитанции, отзыв/удаление,
   аналитику после выбора, сроки журналов и копий, доступ к приватным файлам.
   Не заявлять эти меры реализованными только на основании документа.
10. Согласовать тест на 100 одновременных синтетических пользователей стенда,
    определить допустимую задержку и ошибки, проверить CPU/RAM/соединения/диск
    и выдачу видео. Такой тест ещё не проводился. Проверить восстановление
    из новой копии на другом закрытом экземпляре.

## Условия переключения

Отдельное разрешение владельца, пройденная репетиция и журнал результатов;
свежая согласованная копия и окно остановки записи/сверки дельты; проверенные
OAuth/SMTP, секреты и URL; достоверные документы и уведомления. Уведомление РКН,
по сообщению владельца, ещё не подано. Подготовка миграции не создаёт законной
отсрочки; текущую обработку и возможные нарушения нужно урегулировать отдельно.

Переключать только после проверки базового URL, auth callback, Storage,
Edge Functions, всех native-модулей и GitHub Actions: старый workflow не должен
снова развернуть сборку с иностранным backend. DNS/proxy и сторонние получатели
проверяются явно; GitHub как хранилище кода не равнозначен пользовательской БД.

При сбое не возвращать новые пользовательские записи в иностранную базу
автоматически. Предусмотреть согласованный режим временной остановки записи.
Удаление старого проекта, архивов и секретов — отдельное решение после
приёмки, проверки обязательного хранения и безопасного уничтожения.
