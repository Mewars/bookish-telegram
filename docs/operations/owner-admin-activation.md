# Подключение главного администратора «Рядом» (контрольный план)

**Состояние 14 октября 2026 года:** Production: только профили/избранное; `organizations`, `city_admin_access`, `city_directory` отсутствуют. `VITE_ADMIN_PANEL_ENABLED` и `VITE_CITY_DIRECTORY_ENABLED` пока выключены. Тестовый Supabase Ryadom-Test: 25 организаций, 2 города, таблицы уже созданы, `city_admin_access` пустая.

## Порядок безопасного запуска

1. **Идентификация owner.** В рабочем Supabase Dashboard → Authentication → Users открыть именно учетную запись владельца, через которую он входит на `ryadomcity.ru` (сейчас VK ID). Сверить **Auth User UID** с провайдером `custom:vk`; отображаемое имя не используется как критерий. В документации проекта и git никогда не сохранять настоящий UID, адреса электронной почты и секреты.
2. **Подтвердить возможность восстановления бэкапа.** Есть созданный локально `pg_dump` в формате custom, но `pg_restore --list` проверяет только архив. Восстановление *в отдельное изолированное окружение* ещё не проверено. Не выполнять опасные операции в production ради проверки. Нужен успешный тест восстановления с проверкой структуры/основных строк и отсутствия чувствительных данных в публичных файлах.
3. На отдельной тестовой БД RLS-правила организаций/фото/городов уже развернуты; независимо тестируются в `tests/admin-rls.test.mjs` и `tests/city-directory-rls.test.mjs`. Проверить данные, Storage и роли; не выдавать роли случайным учётным записям.
4. **Только после этапов 1–3 и подтверждения владельца** применить в рабочей базе ранее проверенные additive SQL файлы в порядке `docs/sql/organizations.sql`, `docs/sql/organizations-seed.sql`, `docs/sql/organizations-seed-reviewed-2026-10.sql`, `docs/sql/city-admin-mvp.sql`, `docs/sql/city-directory-multicity.sql`. Порядок seed и актуальные версии сверить с тестовой базой; **первый запуск не должен перезаписывать/возрождать архивные организации**. Не применять миграции к `auth.*`, `profiles`, `user_favorites` и `user_identities`.
5. Выдать доверенным серверным SQL-запросом ровно одну запись `city_admin_access (user_id = verified Auth UID, city='*', role='owner', active=true)`. Запрос выполняется один раз с контролем результата. Все остальные пользователи без административных прав. Не выдавать доступ автоматически по email, имени или наличию VK-сессии.
6. Проверить, что owner видит админку, может добавлять/редактировать карточки с собственными фотографиями; посетитель видит только опубликованное; редактор города не может видеть другой город. `VITE_ADMIN_PANEL_ENABLED` включать только после этого и проверить внешние обращения к Supabase. `VITE_CITY_DIRECTORY_ENABLED` отдельно после проверки добавления городов. Не включать карточки по ложным фотографиям.
7. Создать тестовую резервную копию и план отката. При неожиданных ошибках выключить `VITE_ADMIN_PANEL_ENABLED`, не удаляя таблицы и профили.

## Что делать нельзя

- Назначать роль owner по отображаемому имени, почте, фотографии или идентификатору ВКонтакте вместо внутреннего `auth.users.id`.
- Передавать `service_role`, Supabase secret key, пароль PostgreSQL в frontend, репозиторий или чат.
- Пытаться вернуть дамп поверх рабочей базы ради тестирования.
- Включать админку до появления таблиц, проверенных RLS и уникального owner UID.
- Смешивать тестовые и производственные Supabase ключи/домены.

## Проверки, выполняемые из подключенного инструмента (только чтение)

```sql
SELECT
  to_regclass('public.profiles') IS NOT NULL AS has_profiles,
  to_regclass('public.user_favorites') IS NOT NULL AS has_favorites,
  to_regclass('public.organizations') IS NOT NULL AS has_organizations,
  to_regclass('public.city_admin_access') IS NOT NULL AS has_city_admin_access,
  to_regclass('public.city_directory') IS NOT NULL AS has_city_directory;
```

*Этот документ описывает порядок будущих действий; он не включает административный доступ и не применяет SQL автоматически.*
