# Каталог организаций и заявки: подготовка и ручной запуск

Функция **выключена по умолчанию**. Этот PR не устанавливает SQL, не публикует организации, не меняет Supabase Auth, DNS, SSL или хостинг. Существующие 10 реальных мест, их ID и локальный гостевой режим сохраняются.

## Что добавлено

- `organizations`: проверенные сведения организаций, идентификатор, город, контакты, координаты, источник и дата проверки, статус `draft` / `published` / `archived`, даты создания и обновления.
- `organization_applications`: отдельные приватные заявки с автором, полями формы, источником, статусом `pending` / `approved` / `rejected`, согласием и результатом рассмотрения.
- Чтение опубликованных организаций и объединение с локальным каталогом. Совпадение по ID либо нормализованным городу, названию и адресу сохраняет **локальный ID** и существующую иллюстрацию. Серверный ID для исходных 10 мест обязан совпадать с `src/data/places.ts`.
- `#/add-organization`, `#/my-applications`, `#/organization-consent`, кнопка в каталоге и строка профиля. Эти функции недоступны при выключенном флаге.
- Нет загрузки фотографий, платных API, автоматического геокодинга, выдуманных отзывов или подтверждения владения. Новые места используют существующую иллюстрацию, пока фотографии не подготовлены отдельно.

Локальный каталог остаётся постоянной базовой подборкой, а не резервной копией удаляемых серверных строк. Архивирование строки Supabase не скрывает соответствующее исходное локальное место: для удаления/переименования одной из исходных 10 карточек потребуется отдельная согласованная правка локальных данных с сохранением совместимости избранного. Новые серверные места отображаются только при `published` и не сохраняются локально при отключении сервиса. При недоступности Supabase они могут временно отсутствовать в избранном; сами сохранённые ID не удаляются.

## Флаг и HTTPS

`VITE_ORGANIZATIONS_ENABLED=false` в `.env.example`. Отсутствующий флаг также означает выключенное состояние. Включает функцию только точное значение `true`. Это публичная настройка сборки, **не секрет и не механизм защиты**: защищают RLS и разрешения БД.

Даже при `true` публичная HTTP-версия не включает функцию. Исключение — локальная Vite development-среда на localhost/127.0.0.1/::1. HTTP preview production-сборки не является разрешённой средой подачи заявок. Реальный вход на HTTP тестовом хостинге не выполняйте.

По умолчанию никакие запросы к новым таблицам не отправляются; старые Supabase Auth/Favorites продолжают работать как раньше. Выключение флага требует пересборки и ручного размещения новой сборки. Оно не заменяет закрытие доступа к таблицам при инциденте.

## До установки в действующий проект

1. Отдельно согласовать схему, обработку персональных данных, модерацию и сроки хранения. Согласие на заявки — отдельный документ `ORG-APPLICATION-1.0`; существующее согласие аккаунта не заменяется и его версия не меняется.
2. Проверить текст согласия, полномочия оператора, законные основания публикации контактов, условия использования Supabase/технических исполнителей и применимые требования к обработке данных. Юридическую и инфраструктурную готовность проверяет владелец до запуска.
3. Проверить HTTPS и действующий вход через email/Яндекс на конечном домене. Этот PR не меняет callback URL или настройки Auth.
4. Сделать резервную копию и проверить, что таблицы/функции с предложенными именами ещё не существуют. SQL намеренно не маскирует конфликты через `IF NOT EXISTS`; при конфликте остановиться и согласовать адаптацию.
5. Создать **отдельный тестовый Supabase-проект**, а не использовать production для экспериментов. Проверить существующие политики профилей/избранного отдельно; новые SQL-файлы их не меняют.

## Ручная установка в тестовом Supabase

1. Изучить `docs/sql/organizations.sql`. Файл находится в документации, вне каталогов автоматически исполняемых миграций. Ни frontend, ни CI, ни CSV-importer его не выполняют.
2. В SQL Editor **тестового** проекта выполнить файл от доверенной административной роли. Он создаёт две таблицы, индексы, RLS, ограничения колонок и административную функцию публикации в одной транзакции.
3. Отдельно изучить `docs/sql/organizations-seed.sql` и выполнить его вручную в том же тестовом проекте. Он переносит только существующие 10 мест, исходные ID и предоставленные факты. Не добавляет координаты, сайты, фотографии или несуществующие источники. Дата `2026-10-06` и `user_provided` взяты из текущего каталога и не означают независимую проверку. Повторный запуск не перезаписывает уже проверенные строки. Конфликт естественного ключа с другим ID требует ручного разрешения, а не удаления данных.
4. Не выдавать `anon` / `authenticated` дополнительные `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, права на служебные колонки или выполнение административной функции. Не добавлять клиентские поля `admin` / `role`.
5. Использовать в браузере только существующий `sb_publishable_…` ключ и HTTPS URL. Никогда не передавать `service_role` / `sb_secret_…` во Vite, Netlify или ZIP как публичные переменные.

## Обязательная проверка на настоящем тестовом Supabase

Автотесты выполняют SQL в изолированном PostgreSQL/WASM (PGlite) с тестовыми `auth.users`, JWT claims и API-ролями. Они проверяют реальные PostgreSQL-политики и column grants, но не инфраструктуру Supabase, PostgREST, реальные JWT, существующие политики и конфигурацию проекта. **Проверка ниже обязательна до включения.**

Использовать отдельные тестовые аккаунты A и B и настоящий публичный ключ:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Гость читает organizations | Только `published`; `draft` / `archived` скрыты |
| Гость читает/создаёт заявку | Запрещено |
| A отправляет корректную заявку с отдельным согласием | `pending`; в публичном каталоге её нет |
| A открывает «Мои заявки» | Видит свою заявку |
| B читает заявку A через API или её ID | Не получает строку |
| A подменяет applicant_id на B | RLS запрещает вставку |
| A передаёт status=approved, organization_id, reviewed_at или consented_at | Column grants запрещают вставку |
| A обновляет статус/поля заявки или удаляет её | Запрещено |
| A меняет organizations либо вызывает publish_organization_application | Запрещено |
| Повторяется client_request_id у A | Вторая заявка не создаётся |
| Нет согласия/некорректная версия/слишком длинные поля | Отказ БД |
| Доверенный администратор публикует проверенные сведения | Каталог показывает организацию, A видит approved |
| Supabase недоступен/медленно отвечает | Локальные места доступны, форма показывает ошибку, страницы не блокируются |
| Выход или смена аккаунта | Список/форма предыдущего пользователя удаляется из интерфейса |

Проверить также существующий вход, избранное, согласия и восстановление пароля. Браузерная имитация не заменяет эти проверки.

## Заявки и модерация

Форма требует название, город, категорию, адрес, описание и источник информации. Телефон, часы, сайт и VK — необязательны. Сайт/VK должны иметь HTTPS, без логина и пароля; телефон допускает цифры, `+`, пробелы, скобки и дефисы. Поля ограничены по длине и на клиенте, и в БД. Заявитель подтверждает **отдельное** согласие перед отправкой каждой новой заявки. Чекбокс не отмечается автоматически; сервер записывает версию и время.

Заявки не появляются в public catalog сами по себе. Их source_note и идентификатор заявителя не копируются в публичные организации. Заявитель не считается подтверждённым владельцем.

1. Доверенный модератор открывает `organization_applications` в Supabase Table Editor/SQL Editor с административными правами. Не давать такие права заявителям.
2. Проверяет фактическое существование организации, город, категорию, адрес, контакты, допустимость источников и публикации сведений. Не брать данные из внешних карт; не получать координаты автоматически.
3. Ищет организацию по исходному ID и по городу/названию/адресу. Для одной из существующих 10 карточек **использует исходный place-… ID**, а не новый UUID. Для новой организации выбирает стабильный уникальный ID, допустимые символы: латиница, цифры, `_`, `-`, до 160 символов.
4. Готовит отдельный JSON проверенных полей: обязательны `title`, `city`, `category`, `description`, `source_type`, `verified_at`; необязательны `address`, `phone`, `hours`, `website`, `vk_url`, `latitude`, `longitude`, `source_url`. Дату и источники не выдумывать. Координаты либо обе отсутствуют, либо обе реально предоставлены и проверены.
5. Из доверенного SQL Editor вызывает `public.publish_organization_application(application_id, organization_id, reviewed_fields_jsonb, review_message)`. Подставляет реальные значения проверенной заявки; этот документ не содержит готового вызова с вымышленными фактами. Функция работает с правами вызывающего администратора, блокирует pending-строку, проверяет поля и дату, атомарно публикует организацию и ставит заявке `approved`. При ошибке всё откатывается. Клиентским ролям выполнение запрещено; браузерного RPC нет.
6. Обновление существующей организации возможно только этим доверенным действием. Перед ним сравнить все поля: переданный JSON — полный проверенный вариант, отсутствующие необязательные поля очищаются. Новая строка с совпадающим естественным ключом отклоняется уникальным индексом; сохранить правильный прежний ID.
7. Для отказа администратор меняет pending-заявку в доверенном SQL Editor: `status='rejected'`, `reviewed_at=now()`, `organization_id=NULL`, `review_message` — понятное объяснение, видимое заявителю. Выполнять UPDATE с условием `id=<реальный UUID> AND status='pending'` и проверять число затронутых строк. Не записывать в review_message секреты или персональные данные других людей.
8. Для архивации **новой серверной** карточки доверенный администратор устанавливает `status='archived'`. Для исходной локальной карточки см. оговорку о базовой подборке выше.

Автоматическая rate limiting/CAPTCHA, редактор организаций, подтверждение владельца, уведомления и полноценная административная панель в этот этап не входят. Перед масштабированием оценить антиспам, аудит действий модераторов, план хранения/удаления заявок и пагинацию интерфейса. Чтение ограничено 10 000 строками за запросную серию, с серверной пагинацией; превышение лимита даёт безопасную ошибку, а не неполный каталог.

## Включение после согласования

1. Пройти все проверки в тестовом проекте и отдельно согласовать применение SQL в production. Этот PR не даёт автоматического разрешения на установку production-схемы.
2. После ручной установки и проверки production RLS проверить HTTPS и работу действующего аккаунта на конечном домене.
3. В окружении ручной сборки указать `VITE_ORGANIZATIONS_ENABLED=true`, существующие `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`, выполнить проверенную сборку. Флаг подставляется **во время build**. В текущем workflow ZIP для Спринтхоста его нет, поэтому ZIP остаётся с выключенной функцией; изменение build environment workflow потребует отдельной осознанной правки владельцем после согласования.
4. Размещать готовую сборку штатной ручной процедурой, не изменяя DNS, SSL, Auth callbacks или маршруты. Проверить каталог, заявку, профиль и старые функции на desktop и 390 px. Ни GitHub Pages, ни Netlify конфигурация в этом PR не меняются.
5. При проблемах вернуть флаг в `false`, пересобрать и разместить предыдущую/исправленную сборку. Не удалять заявки/пользовательские данные без отдельного решения. Учитывать кеш браузера и повторно проверять версию сборки.

## Проверка без новой базы / Netlify Preview

Обычный PR preview имеет флаг OFF: проверить неизменный hero, 10 мест, поиск, категории, избранное, профиль, вход, юридические страницы, OSM, music и отсутствие кнопок новой функции. Прямые hash-ссылки на новые экраны показывают сообщение, что приём заявок не открыт.

Для локального просмотра интерфейса без реальной базы:

```sh
npm ci
VITE_ORGANIZATIONS_ENABLED=true npm run dev -- --host 127.0.0.1
```

Без Supabase гостевой пользователь увидит предложение войти; каталог сохранит 10 локальных мест и сообщит об ошибке обновления. Реальная отправка и просмотр статусов требуют тестовой базы и настоящей сессии. Автоматические браузерные проверки с подменёнными ответами покрывают форму, сообщения, статусы и адаптацию, но не отправляют данные в Supabase.

```sh
npm run lint
npm run build
npm run test
# Отдельно новые проверки, включая изолированный SQL:
npm run test:organizations
git diff --check
```

Dev-зависимость PGlite используется только тестами и не входит в production JS, ZIP сайта или публичную БД. Исходный SQL также не попадает в `dist`/ZIP. Действующая публикация на Спринтхосте не меняется до отдельного ручного размещения.
