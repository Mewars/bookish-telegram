## Что поисковики и мессенджеры действительно получают

При HTTP GET `/` сервер выдаёт `index.html` с title, description, canonical, OG/Twitter и JSON-LD. Они доступны без выполнения JS. У ботов, не выполняющих JS, нет HTML со списком карточек; noscript показывает только объяснение. Боты с rendering могут увидеть содержимое React, однако доступность ресурсов, очередь rendering и последующее включение в индекс нужно проверять в инструментах поисковиков.

Фрагмент `#/places` или `#/places/id` **не отправляется серверу**. Его нельзя включать в sitemap как отдельную HTML-страницу и нельзя закрыть отдельной директивой robots. Сервер возвращает один HTML; social preview обычно читает его без React и показывает общую карточку сайта, даже для ссылки на конкретное место.

Изменение `document.title`/description полезно для вкладок, истории и доступности. Оно **не решает индексирование карточек** и не гарантирует их предпросмотр в мессенджерах. OG/Twitter остаются статическими метаданными главной и намеренно не объявляют hash-карточку отдельным URL. Для неизвестного id используется «Карточка не найдена», для демонстрационных записей — общие метаданные раздела без извлечения вымышленных фактов.

Удаление canonical из DOM hash-разделов не создаёт отдельную страницу: raw HTML по-прежнему содержит canonical главной. При будущей генерации отдельных HTML каждому реальному URL потребуется собственный canonical; общий canonical на главную нельзя переносить в такие документы.

Не добавлено глобальное `noindex` для общего HTML: оно закрыло бы главную. Исключение из sitemap и robots не являются защитой приватных данных; защита остаётся задачей существующих Auth/RLS. DNS, серверные redirects/rewrite, маршруты, данные, Auth и Метрика в этом этапе не менялись.

## План отдельных SEO-страниц — только предложение

Миграция маршрутов и пререндеринг **не реализованы**. Для обычного статического хостинга предпочтительно исследовать SSG реальных публичных карточек:

1. **HTML для каждого URL.** На build читать проверенный публичный каталог; генерировать `/places/index.html`, `/places/{slug}/index.html` и уникальные title/description/H1/canonical/OG/JSON-LD. HTML должен содержать реальные описание, адрес и ссылки ещё до JS. Directory URLs `/places/slug/` позволяют обычному хостингу отдавать файл без SPA rewrite; поддержку DirectoryIndex/редиректа на завершающий `/` проверить отдельно. JS добавляет интерактивность, сохраняя семантически тот же HTML. Для каталога React DOM string нельзя считать hydration совместимой без проверки.
2. **Правдивые данные.** Учитывать только `real` записи с проверенными public fields. Для events/services не генерировать реальные посадочные страницы, пока демонстрационные данные не заменены достоверными. Статический генератор не должен читать аккаунты, избранное или серверные secrets. В сборке использовать только публичную проекцию каталога.
3. **Идентификаторы и избранное.** Item id остаётся стабильным; slug — отдельное отображение с уникальностью и журналом прежних slug. Нельзя заменять id на slug в guest storage или `user_favorites`: иначе пропадут сохранения. Hash SPA и старые ссылки сохраняются до согласованной миграции.
4. **Старые ссылки.** Сервер не может дать 301 по hash — он не получает фрагмент. Клиентский bridge может распознать только известные публичные `#/places/{id}`, найти slug и выполнить переход на новый URL. Это не HTTP 301. Для прежних pathname/slug уже можно планировать точечные 301 на сервере, отдельной согласованной задачей. Не перенаправлять служебные/неизвестные hash и OAuth fragments общим правилом.
5. **Удалённые/неизвестные карточки.** Не генерировать отсутствующие записи и не отправлять все неизвестные пути на главную с HTTP 200 (soft 404). Для настоящего отсутствия нужен HTTP 404 и полезная error page; для удалений — 404/410 или точечный 301 только при реальной замене. Пользовательские данные/избранное не удалять автоматически. Настройку статического error document на Спринтхосте согласовать отдельно.
6. **Sitemap.** Формировать из реально выпущенных HTML и стабильного canonical origin, без hash/private/demo URL. Дедупликация и escaping XML обязательны; lastmod брать из настоящей даты изменения опубликованного содержания, иначе не указывать. Build должен проверять существование HTML для каждого loc и исключать удалённые записи.
7. **Auth и восстановление.** Домен остаётся прежним; действующие callbacks без необходимости не менять. Root SPA должен продолжать принимать OAuth `code`/PKCE и recovery query/hash до обработки обычной навигации. Bridge нельзя запускать на auth fragments или удалять query/token state. Проверить email callbacks, Yandex OAuth, refresh, signout, recovery и оба вида favorites с тестовыми аккаунтами на HTTPS. Не использовать статически сгенерированную персональную страницу.
8. **Статический хостинг.** Нет request-time SSR, серверных API/секретов и автоматического обновления HTML; изменение каталога требует новой сборки ZIP. Directory URLs/HTTP statuses/cache/redirect rules ограничены возможностями хостинга. Supabase остаётся внешним сервисом, приватные данные — клиентская часть с RLS. Для будущих городов предусмотреть устойчивую URL/slug модель и отдельные sitemap, не меняя текущие URL в этом PR.

## Проверки этого этапа

- Node 24, `npm ci` (workspace npm cache), lint, production build, maps/OSM/import tests и новые SEO tests.
- SEO tests проверяют согласованность static/runtime homepage, отсутствие duplicate meta/canonical, абсолютные public URLs, правдивый WebSite JSON-LD, безопасные fallback/demo тексты и root-only sitemap.
- XML sitemap отдельно разбирается XML parser; все loc — абсолютные HTTPS без hash/служебных экранов, lastmod отсутствует.
- Проверяются `dist/robots.txt`, `dist/sitemap.xml`, JPEG/favicon и сборка ZIP без wrapper `dist/`. Существующий workflow пакует всё содержимое dist, поэтому новые файлы включаются без изменения workflow.
- Локальный Chromium проверяет direct hash navigation, title/description/canonical при смене разделов/карточек и возврате на главную/importer, отсутствие дублей; no-JS browser проверяет raw SEO и noscript. Проверяются 390/1440 px, guest favorites/search и auth через локальную фикстуру без реального HTTP-входа.
- Production HTTPS/SSL, live rendering Google/Яндекс, действующее владение доменом и реальные platform previews не проверены из-за ограниченного доступа и отсутствия owner credentials. Это остаётся ручной проверкой по `seo-webmaster-setup.md`.

См. [инструкцию владельцу](seo-webmaster-setup.md). Перед выпуском проверять готовый ZIP и обновлять сайт обычным согласованным процессом; в рамках этого этапа публикация, подтверждение домена и merge не выполняются.
