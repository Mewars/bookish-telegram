# Истории жителей: выпуск и согласование

## Состояние

Код подготовлен к реальным историям. `docs/sql/city-stories-v1.sql` ещё не применён к Production. При отсутствии схемы блок скрыт; пробный режим `stories=preview` остаётся доступен отдельно. Не считать функцию включённой до разрешения владельца, применения SQL и реальной проверки API.

## Поведение

- Главная и native `/wall/`: отдельная полоса с фото и именами авторов. Без вымышленных историй.
- Автор входит в существующий аккаунт, выбирает JPG/PNG/WebP до 10 МБ и подпись до 200 символов. Клиент заново кодирует изображение в WebP, до 1080×1920 и 2 МБ, удаляя исходные метаданные. Видео не включено.
- До 5 созданий за скользящие 24 часа; квота серверная, удаление её не сбрасывает.
- Фото загружается в приватный новый бакет; проверка наличия объекта и размера перед отправкой. Повтор подтверждённой отправки с той же подписью идемпотентен. При ошибке загрузки форма сохраняет подготовленный файл для повтора.
- История всегда поступает в pending. Автор не может изменять статус напрямую.
- «Мои истории»: статусы, причина отказа, просмотр и удаление. После отказа можно создать новую исправленную историю.
- Городской owner/editor модерирует только свой город. Глобальный owner `*` — любой город. Городской администратор не одобряет себя; глобальный владелец может одобрить свою историю.
- Публикация назначает серверные `published_at` и `expires_at = published_at + 24 hours`. Нельзя заново одобрить уже опубликованную и продлить срок.
- Истёкшие и скрытые истории исключаются из публичных RPC/RLS. Файлы остаются приватными для автора/своей городской команды; физического автоматического удаления/очистки пока нет.
- Публичный ряд показывает до 50 самых свежих действующих историй города. Очереди — до 50 записей; для большего объёма понадобится постраничный просмотр.
- Жалоба: вошедший пользователь, причина 3–500 знаков, одна на историю, до 10 за 24 часа. Команда видит жалобы своего города и может скрыть историю. Автоблокировки по жалобам нет.
- Обновление ряда раз в 30 секунд и при фокусе. Открытый просмотр проверяет истечение срока; фото не обрезается. При смене аккаунта закрываются окна и освобождаются локальные ссылки на фото.

## SQL меняет только новые объекты

Две новые таблицы с RLS: `city_stories`, `city_story_reports`. Один новый PRIVATE бакет `ryadom-stories` (WebP, 2 МБ). Один публичный SECURITY INVOKER RPC для опубликованных историй и пять авторизованных RPC с серверной проверкой автора/города/роли/квот. Их SECURITY DEFINER нужен для контролируемой записи: прямой INSERT/UPDATE/DELETE на таблицы не выдан. EXECUTE у PUBLIC/anon отозван для всех пяти операций записи.

Storage SELECT разрешён для `object.get_authenticated` и видимой записи, а также для `object.delete`/`object.delete_many` при удалении собственного draft/rejected/removed (Storage требует SELECT и для удаления). Подписывание долгих ссылок, листинг и преобразования в этом бакете не разрешены. Ограничительные (RESTRICTIVE) политики защищают новый бакет и от существующих широких PERMISSIVE политик; для остальных бакетов guard возвращает true. UPDATE фото запрещён, загрузка только своего draft через `object.upload` (подписанные загрузки также запрещены), удаление файла только своего draft/rejected/removed. Веб-клиент использует download + временный Blob URL, не signed URL. Как и в любой ленте, уже скачанное изображение пользователь может сохранить.

Существующие таблицы, пользователи, назначения ролей, настройки Auth и другие бакеты не изменяются. SQL транзакционный, одноразовый: при уже существующем объекте остановится, а не перезапишет его.

## Проверки

- `node --test tests/city-stories.test.mjs`: фактический SQL в изолированном PGlite, роли anon/resident/city editor/global owner. Запрет прямой записи/самоодобрения, изоляция городов/черновиков/жалоб, причина отказа, повторная отправка, квота после удаления, 24 часа, Storage signing/listing/update/чужая загрузка при намеренно широких старых политиках.
- `python tests/stories-live-browser.py`: реальный UI/canvas и синтетический API в памяти, отправка → pending → одобрение → гость, смена города/аккаунта, подпись как текст. Это не реальная Supabase Storage HTTP-проверка.
- Существующие тесты главной, стены, объявлений и сборки.

После разрешения: применить точный SQL, выполнить read-only проверки прав/бакета/API и согласованный сценарий с тестовой историей владельца. Не писать историю от имени владельца и не создавать реальные пользовательские материалы без отдельной команды. До проверки на hosted Storage не заявлять полную проверку реальной загрузки. План отката без потери данных: скрыть frontend-блок обратным кодовым коммитом, оставить новые приватные таблицы и бакет; не удалять пользовательские фото/таблицы.
