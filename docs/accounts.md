# Аккаунты Рядом и Supabase

## Подключение

Единый клиент находится в `src/lib/supabase.ts`, официальный пакет — `@supabase/supabase-js`. `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` используются в браузере. Конфигурация принимает HTTPS URL и публичный ключ с префиксом sb_publishable_. Неподходящие или отсутствующие переменные возвращают null: клиент не создаётся, приложение работает как guest, dev console предупреждает без вывода значений. Переменные Netlify встраиваются при сборке и не появляются автоматически в локальной cloud-среде.

SUPABASE_SECRET_KEY, service_role, secret key, OAuth client secrets, пароль БД и Bot Token не используются клиентом и не должны попадать в VITE-переменные или Git. Публичный ключ не обходит RLS. Frontend не обращается к auth.users напрямую и не применяет schema.sql.

## Lifecycle сессии

AuthProvider подписывается на supabase.auth.onAuthStateChange и вызывает getSession при старте. Без сессии — guest; при наличии сессии — authenticated с auth.user.id. Запросы к profiles и user_identities выполняются после получения сессии. Профиль может временно отсутствовать: null сохраняется явно, UUID аккаунта остаётся известным, интерфейс не имитирует гостя или вымышленный профиль.

Асинхронные запросы отложены вне callback onAuthStateChange, чтобы не блокировать auth lock SDK. Каждое событие повышает revision; ответы старой сессии не могут восстановить профиль после logout или смены пользователя. При unmount subscription отписывается, таймеры очищаются, устаревшие ответы игнорируются. TOKEN_REFRESHED и SIGNED_IN обновляют данные профиля. SDK восстанавливает и обновляет Supabase session своим стандартным механизмом persistSession/autoRefreshToken. OAuth provider tokens приложение отдельно не хранит.

signOut вызывает настоящий supabase.auth.signOut. Успешный logout очищает user/profile/identities; при ошибке UI показывает сообщение без фиктивного успеха. Гостевой localStorage и аккаунтный кеш не уничтожаются. Они разделены, чтобы данные аккаунта не попадали в гостевой список.

## Профиль и identities

profiles.id — стабильный UUID auth.users.id. Профиль создаётся database trigger из schema.sql только с id; непроверенная metadata провайдеров не копируется. Все способы входа принадлежат тому же UUID через user_identities.user_id, пара provider/provider_user_id уникальна глобально.

readAccountData читает только профиль с id текущего пользователя и его identities. updateProfile доступен через useAuth и отправляет строго display_name/avatar_url/city. Runtime allowlist исключает id/created_at/updated_at, даже если дополнительные поля переданы из JavaScript. Запрос проверяет текущую Supabase session и фильтрует id. RLS и grants защищают строки и столбцы на сервере. Identity-клиент выполняет только SELECT: связывание и удаление остаются задачей доверенного backend.

## Избранное

Для гостя useFavorites использует прежний ключ ryadom.favorites и тот же формат массива ID. Для authenticated используется AccountFavoritesRepository на public.user_favorites. Каждый запрос проверяет текущую сессию и ограничен user_id; DELETE дополнительно ограничен item_id.

Первый успешный вход с данного браузера получает серверный список и локальные гостевые ID. mergeGuestFavorites добавляет только отсутствующие ID атомарным upsert с ignoreDuplicates (INSERT ... ON CONFLICT DO NOTHING), затем перечитывает сервер. Пустой localStorage никогда не очищает сервер. Объединённый список сохраняется в ryadom.favorites.account.<UUID>; после успешной синхронизации ставится отметка ryadom.favorites.imported.<UUID>. Гостевой список остаётся нетронутым. Отметка предотвращает повторный импорт уже удалённых на сервере гостевых ID при reload или повторном входе. После очистки данных браузера импорт может повториться.

Первичная синхронизация блокирует сердечки до завершения, чтобы не потерять изменения во время merge. Затем изменения UI оптимистичны: последовательная очередь отправляет INSERT/DELETE, а UI строится из подтверждённого списка и ожидающих действий. Ошибка откатывает только неуспешное действие, не уничтожая последующие намерения. Кеш хранит подтверждённый список. При смене аккаунта/выходе очередь старой сессии перестаёт выполняться, её ответы не меняют новый UI. Отдельный кеш не выдаёт данные другого аккаунта гостю.

Ошибки чтения или изменения отображаются с кнопкой повтора. Если localStorage недоступен, серверная работа может продолжаться, но кеш и отметка импорта не сохранятся; UI предупреждает о локальном сохранении. В гостевом режиме находки доступны до закрытия приложения. RLS проверяет auth.uid(), а не доверяет userId из параметров клиента.

## Что остаётся неподключённым

Страница #/login запускает реальный OAuth только для Яндекс ID (`custom:yandex`). VK/Telegram/Google отключены, MAX — скоро. Нет mock login или собственной фиктивной сессии. Данные Telegram initDataUnsafe служат только отображению. getTelegramIdentityRequest подготовлен для будущего HTTPS POST с серверной проверкой подписи initData, auth_date и ограничений повтора; сейчас он не отправляется на сервер и не создаёт Supabase session.

Следующие этапы: серверная проверка Telegram, отдельное подключение OAuth, безопасное связывание identities с повторным подтверждением пользователя, UI редактирования профиля и интеграционные проверки действующего проекта Supabase. Связывание нельзя делать по отображаемому имени или неподтверждённому email. База и RLS уже настроены пользователем; приложение их не меняет.

## Проверки и ограничения среды

Без env можно проверить production guest, desktop/mobile, Telegram mock, login и localStorage. Для проверки клиентских запросов и событий SDK используются изолированные HTTP fixtures вне исходников приложения; это не функция входа. Для проверки действующих Supabase RLS и настоящей серверной сессии нужен отдельный тест в настроенном окружении. Локальная cloud-среда не содержит значений Netlify env, поэтому успешный тест HTTP fixtures не доказывает подключение к действующей базе или корректность её RLS.

## Yandex ID: нормализация Userinfo

Edge Function `supabase/functions/yandex-userinfo/index.ts` принимает GET от Supabase Auth с `Authorization: Bearer <yandex_access_token>`. Этот Bearer передаётся только на `https://login.yandex.ru/info?format=json`. Функция возвращает нормализованные OIDC-поля sub/email/email_verified/name/given_name/family_name/preferred_username/picture. При отсутствии email поле опускается; при отсутствии аватара picture равен null. Некорректный или отсутствующий id не превращается в фиктивный sub.

Для этой функции в `supabase/config.toml` установлено `verify_jwt = false`: входящий token принадлежит Яндексу, не Supabase. Проверка JWT остальных функций не изменяется. Наличие корректного Yandex token проверяется самим Яндексом; без Bearer функция возвращает 401, другие методы — 405. Ошибочный HTTP status Яндекса сохраняется с нейтральным JSON-ответом, без передачи его тела или заголовков. Сетевая ошибка/некорректный JSON даёт 502, timeout — 504. Ответы имеют Cache-Control: no-store. Токен и Authorization не логируются и не сохраняются, client secret и Supabase secret key функции не нужны.

На отдельном этапе deploy можно выполнить из корня проекта через настроенный Supabase CLI:

```bash
supabase functions deploy yandex-userinfo --project-ref <project-ref>
```

После deploy URL будет:

```text
https://<project-ref>.supabase.co/functions/v1/yandex-userinfo
```

Указать этот адрес в Custom OAuth Provider как **Userinfo URL**. Client ID / Client Secret провайдера настраиваются отдельно на серверной стороне Supabase, не в frontend или Git. Deploy в рамках этой задачи не выполнялся; Custom OAuth Provider `custom:yandex` включён пользователем; web-кнопка Яндекс ID активна.

## Вход через Яндекс ID

Кнопка Яндекс ID вызывает `supabase.auth.signInWithOAuth({ provider: 'custom:yandex', options: { redirectTo: window.location.origin + '/' } })`. Client ID и Client Secret остаются в настройках Supabase. На время запуска кнопка показывает «Переходим в Яндекс…» и блокирует повторные клики. Ошибка до redirect отображается без технических деталей или значений токенов. Без env приложение остаётся гостевым и показывает понятное сообщение при попытке входа.

SDK использует PKCE и detectSessionInUrl: callback с code обменивается на настоящую Supabase session, code удаляется из URL, а существующий AuthProvider через getSession/onAuthStateChange загружает профиль. Корневой URL сайта должен быть разрешён в Supabase Auth Redirect URLs; для другого домена нужно добавить его origin с завершающим `/`. Браузерное хранилище сохраняет Supabase session и PKCE state, но исключает provider_token/provider_refresh_token Яндекса. При недоступном localStorage используется память, и сессия не сохраняется после закрытия страницы.

Пустые display_name/avatar_url существующего профиля могут один раз заполниться из metadata пользователя, проверенного через Supabase getUser. Используются name/full_name/preferred_username и picture/avatar_url, только для пользователя с провайдером custom:yandex. Уже заполненные поля не меняются; условный UPDATE также защищает от пользовательской правки во время запроса. Обновление выполняется через существующий updateCurrentProfile по текущему UUID. Отметка инициализации хранится локально по UUID; после очистки хранилища проверка может повториться, но непустые поля всё равно защищены. SQL-схема не менялась.


## Email + пароль (новый интерфейс)

В \`#/login\` доступны три вкладки/состояния: вход по email, регистрация и запрос восстановления. Используются стандартные Supabase Auth \`signInWithPassword\`, \`signUp\`, \`resetPasswordForEmail\`, \`updateUser\`. Никакие пароли не отправляются на собственный backend, не записываются в localStorage и не логируются. Текущие Яндекс ID и гостевой режим сохраняются. Регистрация и Яндекс требуют прежнего отдельного согласия; вход существующего аккаунта и восстановление пароля не требуют повторного согласия.

Восстановление направляется на корневой URL сайта с параметром \`ryadom_recovery=1\` и hash \`#/login\`. После подтверждения сессии показывается форма нового пароля. После успешного обновления параметр удаляется из адресной строки. Этот URL должен быть разрешён в Supabase Auth Redirect URLs. Не следует добавлять в whitelist произвольные посторонние домены.

**Ручная настройка в Dashboard Supabase:** Authentication → Providers → Email: включить email-авторизацию, регистрацию и подтверждение email; проверить почтовые шаблоны и способ отправки писем. Authentication → URL Configuration: указать \`https://ryadomcity.ru/\` как Site URL и разрешить \`https://ryadomcity.ru/\`, а также \`https://ryadomcity.ru/?ryadom_recovery=1\` в Redirect URLs. Для надёжной массовой рассылки потребуется настроить допустимый SMTP-провайдер; стандартная почтовая служба Supabase имеет ограничения. Эти действия не выполнялись в рамках PR.

Email может совпадать с адресом существующей учётной записи Яндекса. **Объединение разных пользователей, созданных разными способами входа, автоматически не реализовано** — не предполагайте, что такая регистрация связывает два аккаунта. Настоящие email-delivery, подтверждение и смену пароля необходимо проверить в действующем проекте после настройки Dashboard.
