# Защита от автоматического спама

Общий модуль `/security/antispam.js` запрашивает проверку при email-входе, регистрации, восстановлении пароля, отправке объявления, записи/комментария стены и заявки организации. При отмене или ошибке данные формы сохраняются. VK ID и Яндекс ID продолжают собственную авторизацию.

Supabase Auth проверяет токен сам. Для контента Edge Function `ryadom-antispam` проверяет JWT через Auth, затем одноразовый токен Cloudflare Siteverify, точный hostname и action. Только служебная роль выдаёт разрешение записи. Триггеры БД требуют разрешение даже при прямом REST/RPC-запросе. Разрешение связано с пользователем, видом формы и ID: позволяет создать одну карточку и отправить именно её на модерацию; срок 15 минут для загрузки вложений. Повторная отправка существующего черновика получает отдельное разрешение. Модерация и городские права остаются обязательными.

## Включение

Пока реальные ключи не настроены, защита **выключена**. Отсутствующий серверный RPC определяется только по конкретным кодам отсутствия функции; остальные ошибки блокируют отправку.

1. Создать Managed Turnstile widget для `ryadomcity.ru` и `www.ryadomcity.ru`. Не использовать тестовые ключи в Production. Не включать pre-clearance и не менять DNS.
2. Сохранить Secret key только в Supabase Auth CAPTCHA (провайдер Turnstile) и в Edge Function secret `TURNSTILE_SECRET_KEY`. Не помещать его в GitHub, клиентский код, скриншоты, логи или документы. `TURNSTILE_ALLOWED_HOSTNAMES=ryadomcity.ru,www.ryadomcity.ru`. Встроенные Supabase server environment keys уже предоставляет платформа.
3. Применить `docs/sql/antispam-turnstile-v1.sql` сначала в Test, проверить ACL/триггеры, затем согласованно в Production. Схема private, RLS включена, пользователь не может выдавать разрешения. Начальные флаги выключены.
4. Развернуть новую Edge Function с собственной JWT-проверкой (`verify_jwt=false`: обработчик проверяет токен через Auth до выдачи разрешения). Существующие функции не менять.
5. Опубликовать обе версии клиента — React и самостоятельные объявления/стену. Предварительно проверить Siteverify на реальном домене. Тесты CI используют только имитацию виджета и изолированную БД, не реальные CAPTCHA.
6. В private settings записать публичный Site key и включить `content_enabled`; затем включить CAPTCHA в Supabase Auth и `auth_enabled`. Изменения флагов и ключей выполнять согласованно. До успешного реального сценария не объявлять защиту активной.

## Проверки и откат

Проверить регистрацию/вход/восстановление, повтор после ошибки, отправку с фото и без фото, комментарии, нового/существующего пользователя и разные города. Проверить, что REST/RPC без разрешения, чужое разрешение, повторное разрешение, чужой hostname/action и просроченный токен отклоняются. Проверить owner moderation и новости администрации.

Публичная конфигурация содержит только Site key и два флага. SECURITY DEFINER здесь необходим для чтения private config и проверки разрешения, права EXECUTE явно ограничены. Secret key в БД не хранится.

При неисправности сначала отключить CAPTCHA в Auth и флаги в private settings; затем откатывать клиент. Не удалять таблицы, записи жителей, существующие функции или RLS. Старые открытые вкладки после включения могут потребовать обновить страницу. При недоступности Cloudflare форма сообщает об ошибке, не отправляет материал и сохраняет текст.
